# Root Cause Debugging — 根因调试

## 核心理念

**先查根因，再动手修复。症状修复等于失败。**

调试非试错游戏，乃**取证调查**。凡「快速试一下」「改改看」之冲动，皆须拦截。

> 本 skill 移植自 obra/superpowers 的 `systematic-debugging`（MIT License），结合 pi 平台与实战经验调整。原文理念：
> **"Violating the letter of this process is violating the spirit of debugging."**
> （违背本流程字面条款，即违背调试精神）

---

## Iron Law（铁律）

```text
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

**Phase 1（根因调查）未毕，禁提任何修复方案。**

违反铁律之典型形态：
- 见报错即改代码
- 先加 try-except 包住再说
- 换 seed 重跑试试（ML 训练典型症状修复）
- 搜到相似错误即照抄 stackoverflow 答案

---

## 适用场景

**任何**技术问题皆须走本流程（豁免情形见「适用边界与豁免」一节）：
- 测试失败
- 生产环境 bug
- 意外行为（IC 异常、loss 不降、显存暴涨）
- 构建失败
- 集成问题
- 训练结果不符预期（与 `quant-ml-falsification.md` 配合：先查代码/数据，再疑 alpha）

**尤其必须使用**：
- 时间压力下（紧急最易乱猜）
- 「就一个快速修复」看似显然之时
- 已试多个修复皆未成功
- 上次修复未生效
- 未完全理解问题

**勿跳过**：
- 问题看似简单（简单 bug 亦有根因）
- 很急（系统化比乱撞快）
- 用户催着马上修（系统化修复比反复打补丁快）

## 四阶段流程

各阶段须按序完成，方可进入下一阶段。

### Phase 1：根因调查（禁止跳过）

**修复之先**：

1. **细读错误信息**
   - 勿跳过任何错误/警告
   - 错误信息常直接含答案
   - 完整读堆栈：行号、文件路径、错误码
   - 读至最后一行，勿只看第一屏

2. **稳定复现**
   - 能否稳定触发？精确步骤为何？
   - 每次皆发生？
   - 无法复现 → 收集更多数据，勿猜

3. **检查近期变更**
   - 何改动可能致此 bug？
   - `git diff`、最近提交
   - 新依赖、配置变更、环境差异
   - 服务器 vs 本地版本漂移（`md5sum` 对比三端代码）

4. **多组件系统取证（组件边界插桩）**

   系统有多组件时（CI → 构建 → 签名；数据 → 特征 → 模型 → 奖励 → 训练）：

   **提出修复前，先加诊断插桩**：
   ```text
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置是否传播
     - 检查每一层的状态

   先跑一次收集证据，定位故障组件
   再针对该组件深入调查
   ```

   **VERSION2.5 实例**：`scripts/audit_forward_leak_multi.py` 即组件边界插桩典型——对每个特征分别算 fwd IC 与 bwd IC，比值 6.2 直接暴露 `t_corr` 前瞻泄露。无插桩，恐永远在「换特征池」上打转。

5. **反向追踪数据流**

   错误出现于调用栈深处时：
   - 坏值从何而来？
   - 谁将此坏值传入？
   - 沿调用链一路向上，直至源头
   - **修源头，勿修症状**

### Phase 2：模式分析（找出差异）

1. **找正常之例**：同代码库中相似且正常工作之代码
2. **对照参考实现**：实现某模式时，完整读参考实现——一行勿跳
3. **列出差异**：正常与异常差在何处？差异皆列出，哪怕再小——勿想当然「此不影响」
4. **理解依赖**：此组件依赖什么？需何配置/环境？有何隐含假设？

### Phase 3：假设与验证（科学方法）

1. **形成单一假设**
   - 明确写出：「我认为 X 是根因，因为 Y」
   - 写下来，要具体，勿模糊
2. **最小化验证**
   - 做**最小**改动以验证假设
   - **一次只改一个变量**
   - 勿同时修多个东西
3. **验证后再继续**
   - 有效 → 进入 Phase 4
   - 无效 → 形成新假设
   - **勿在上面叠加更多修复**
4. **不知即言不知**
   - 说「我不理解 X」，勿装懂
   - 请求帮助，继续研究

### Phase 4：实施修复

**修根因，勿修症状**：

1. **先创建失败测试用例**
   - 最简单之复现（自动化测试优先，无测试框架则一次性脚本）
   - **修复前必须有**（衔接 `development-quality-gates.md` 关卡 6）
2. **实施单一修复**
   - 只改一处
   - 勿「顺手优化」，勿捆绑重构
3. **验证修复**
   - 测试通过否？
   - 其他测试被破坏否？
   - 问题真正解决否？
   - 声称成功前使用 `verification-before-completion.md`
4. **若修复无效**
   - **暂停修复**
   - 数一数：已试几次修复？
   - < 3 次 → 带新信息回到 Phase 1
   - **≥ 3 次 → 升级为质疑架构**（见下）
   - 未经架构讨论，勿试第 4 次

5. **3 次以上修复失败 → 质疑架构**

   架构问题之信号：
   - 每次修复皆暴露新的共享状态/耦合问题
   - 修复需「大规模重构」
   - 每次修复皆在别处生新症状

   **停下来质疑根本**：
   - 此模式本身站得住否？
   - 是否「因惯性硬撑」？
   - 应重构架构，抑或继续修症状？

   **先与用户讨论，再试更多修复**。此非失败之假设——此乃错误之架构。

### 「3 次失败」语义（重要）

`max_fixes_before_architecture_review`（front matter，默认 3）**是升级信号，不是硬停止**：

- 触达阈值 → 暂停自动修复，升级为「质疑架构」讨论
- 用户判断场景后可继续修复（如超参搜索场景 3 次远未到底）
- 阈值可按项目在 inputs 中覆盖
- 默认值 3 是启发式，非普适定律

## Red Flags（红旗）— 立即暂停并走流程

脑中有此念，即汝在合理化跳流程：

| 想法 | 现实 |
|------|------|
| "先快速修一下，之后再调查" | 症状修复，回去调查 |
| "改个 X 试试看行不行" | 没有假设的乱试 |
| "加多个改动，一起跑测试" | 变量混淆，无法定位 |
| "跳过测试，我手动验证" | 跳过验证=没验证 |
| "这个错误看起来很眼熟，以前见过" | 记忆不可靠，重新取证 |
| "再换个 seed 跑一次" | 没有根因的赌博 |
| "应该是数据问题吧，重新拉一次数据" | 没有证据的猜测 |
| "紧急情况，先修上再说" | 紧急时最需要系统化 |
| "我已经很接近了，再试一次" | ≥3 次就升级质疑架构 |

## 适用边界与豁免

本 skill 约束调试行为，非约束一切。以下情形可豁免或降级：

| 情形 | 处理 |
|------|------|
| 一次性脚本 / 探索性实验 | Phase 4 失败测试降级为一次性验证脚本 |
| 用户明确指示「直接修」 | 用户指示优先，修复中注明已跳过根因调查 |
| 被派发的 subagent 执行具体修复 | 任务文本已含调查结论，只执行 Phase 4 |
| 超参搜索 / seed 敏感性排查 | 「3 次失败」阈值视为升级信号，非硬停止 |
| 项目已有调试约定 | 项目约定优先，本 skill 降级为参考 |

## 作业要求

```text
发现 bug → Phase 1 根因调查（读错误/复现/查变更/插桩取证）→ Phase 2 模式分析 → Phase 3 单一假设最小验证 → Phase 4 失败测试 + 单一修复 + 验证 → 记录根因（为何、如何查到、修了什么）
```

1. 每次修复后，在 commit message 与文档中记录**根因**，不只记录改了什么
2. 3 次修复失败 = 升级质疑架构 + 与用户讨论（非硬停止，见上文语义）
3. 症状修复之标志：同一定位点反复出问题 → 根本未找到根因
